# 소프트웨어 엔지니어링 핵심 법칙 (Software Engineering Laws and Principles)

소프트웨어 엔지니어링 법칙은 시스템, 코드, 팀 운영에서 반복적으로 나타나는 실패 패턴을 미리 알아보게 해주는 실무 사고 도구이다. 여기서 "법칙(Law)"은 자연법칙처럼 절대적인 것이 아니라, 수십 년에 걸쳐 관찰된 경험칙(Empirical Heuristic), 정리(Theorem), 원칙(Principle), 규칙(Rule)을 통칭한다. 본 문서는 시스템 설계·코드 품질·팀 운영 세 영역에서 자주 인용되는 대표 항목들을 정리한다.

---

## 0. 용어 정리 — Law · Theorem · Principle · Rule

| 구분 | 성격 | 본 문서 예시 |
|------|------|--------------|
| Law (법칙·경험칙) | 반복 관찰된 사회·기술적 경향. 반증 가능하지만 잘 들어맞는다 | Conway's, Gall's, Hyrum's, Brooks's, Hofstadter's, Goodhart's |
| Theorem (정리) | 형식적으로 증명된 명제 | CAP Theorem |
| Principle (원칙) | 설계·구현 시 따르기로 약속한 규범 | YAGNI, DRY, KISS, SRP, Postel's, Pareto, Law of Demeter |
| Rule (규칙·관행) | 팀·커뮤니티가 합의한 행동 지침 | Boy Scout Rule |
| Aphorism (격언) | 비유적·계몽적 진술 | Law of Leaky Abstractions |

## 1. 시스템 아키텍처

구조가 점점 복잡해지고 변경이 어려워지는 문제를 다룬다. 분산·확장·계약의 본질을 짚는 항목들을 묶었다.

### 1.1 Conway's Law (콘웨이의 법칙)

| 항목 | 내용 |
|------|------|
| 원어 | "Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure." (Melvin Conway, 1968) |
| 핵심 주장 | 조직의 커뮤니케이션 구조가 결국 시스템 구조에 반영된다 |
| 적용 예시 | 4개 팀이 컴파일러를 만들면 4-패스 컴파일러가 나온다. MSA를 도입했는데 팀이 모놀리식 위계라면 서비스 경계가 팀 경계를 따라간다 |
| 실무 활용 | 역(逆) 콘웨이 전략(Inverse Conway Maneuver) — 원하는 아키텍처를 먼저 결정하고 그에 맞춰 팀 구조를 설계한다 |

### 1.2 Gall's Law (갈의 법칙)

| 항목 | 내용 |
|------|------|
| 원어 | "A complex system that works is invariably found to have evolved from a simple system that worked." (John Gall, 1975) |
| 핵심 주장 | 잘 동작하는 복잡한 시스템은 잘 동작하던 단순한 시스템에서 진화한다. 처음부터 복잡하게 설계한 시스템은 거의 동작하지 않는다 |
| 적용 예시 | 초기부터 MSA로 나눈 결과 배포·장애 추적이 더 어려워진 사례. 모놀리스로 검증한 뒤 경계가 분명해진 부분만 떼어내는 편이 안전하다 |
| 안티패턴 | "처음부터 완벽한 설계" — 검증되지 않은 복잡성은 회복하기 어렵다 |

### 1.3 Hyrum's Law (하이럼의 법칙)

| 항목 | 내용 |
|------|------|
| 원어 | "With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody." (Hyrum Wright) |
| 핵심 주장 | 사용자가 충분히 많아지면 문서화되지 않은 동작·우연한 동작까지 누군가의 의존성이 된다 |
| 적용 예시 | API 응답 필드 순서를 바꿨더니 일부 클라이언트가 깨졌다. 정렬·공백·에러 메시지 포맷처럼 명세에 없는 부분에도 의존성이 형성된다 |
| 실무 활용 | 변경 영향도 평가 시 "명세상 호환" 만 보지 말고 관찰 가능한 동작 전반을 검토한다. SemVer의 patch도 클라이언트를 깰 수 있다 |

### 1.4 CAP Theorem (CAP 정리)

| 항목 | 내용 |
|------|------|
| 원어 | "Of Consistency, Availability, and Partition tolerance, a distributed system can guarantee at most two." (Eric Brewer, 2000) |
| 핵심 주장 | 분산 시스템은 일관성(Consistency), 가용성(Availability), 분할 내성(Partition Tolerance)을 동시에 완벽히 만족할 수 없다. 네트워크 분할은 현실적으로 피할 수 없으므로 실질적 선택은 CP 또는 AP이다 |
| 적용 예시 | 금융 거래 시스템은 CP(분할 시 가용성 희생) — 일관성 우선. 소셜 피드는 AP — 최신성보다 응답 우선 |
| 보완 개념 | PACELC — 분할(P)이 없을 때도 지연(Latency, L)과 일관성(C) 사이의 트레이드오프가 존재한다 |

### 1.5 Postel's Law (포스텔의 법칙 / Robustness Principle)

| 항목 | 내용 |
|------|------|
| 원어 | "Be conservative in what you send, be liberal in what you accept." (Jon Postel, RFC 760·793) |
| 핵심 주장 | 보낼 때는 명세를 엄격히 지키고, 받을 때는 명세에서 벗어난 입력에도 관대하게 동작한다 |
| 적용 예시 | HTML 파서가 깨진 태그도 렌더링하는 관행. HTTP 헤더 대소문자 무시 |
| 트레이드오프 | 지나친 관대함은 명세 일탈을 양산해 결과적으로 호환성 문제를 키운다는 비판(IETF의 후속 논의)이 있다. Hyrum's Law와 결합하면 "관대한 수용"이 곧 영구적 부채가 된다 |

## 2. 설계와 코드 품질

필요 없는 기능, 중복, 과한 추상화, 강한 결합이 쌓이는 문제를 다룬다.

### 2.1 YAGNI (You Aren't Gonna Need It)

| 항목 | 내용 |
|------|------|
| 출처 | Extreme Programming (Kent Beck, Ron Jeffries, 1990s) |
| 핵심 주장 | 지금 필요하지 않은 기능은 미리 만들지 않는다. 미래 추정보다 현재 요구에 집중한다 |
| 적용 예시 | "언젠가 다국어 지원이 필요할 것 같다"며 i18n 계층을 미리 깐 결과, 정작 요구사항이 왔을 때 추상화가 맞지 않아 다시 만든다 |
| 주의 | YAGNI는 "확장성 무시"가 아니다. 검증되지 않은 추측에 비용을 쓰지 말라는 것이지, 명백한 요구를 외면하라는 뜻이 아니다 |

### 2.2 DRY (Don't Repeat Yourself)

| 항목 | 내용 |
|------|------|
| 출처 | Andy Hunt, Dave Thomas — *The Pragmatic Programmer* (1999) |
| 핵심 주장 | "모든 지식은 시스템 내에서 단 하나의 명확하고 권위 있는 표현을 가져야 한다." 중복은 코드의 중복이 아니라 **지식(knowledge)의 중복**을 말한다 |
| 적용 예시 | 비즈니스 규칙이 프론트·백·DB 트리거 세 곳에 같은 로직으로 흩어져 있으면, 변경 시 한 곳을 놓쳐 버그가 난다 |
| 안티패턴 | 우연히 비슷해 보이는 코드를 무리하게 합치는 "성급한 추상화". 같은 모양이라도 변화 축이 다르면 분리해야 한다 (참고: WET, AHA 원칙) |

### 2.3 KISS (Keep It Simple, Stupid)

| 항목 | 내용 |
|------|------|
| 출처 | Kelly Johnson, Lockheed Skunk Works (1960s) |
| 핵심 주장 | 설계와 구현은 가능한 한 단순하게 유지한다. 단순함은 이해·수정·디버깅 속도를 높인다 |
| 적용 예시 | 콜백 4단 중첩보다 평탄한 함수 호출. "유연성"을 위한 플러그인 시스템보다 if-else 두 줄 |
| 주의 | "단순함"은 "쉬움"과 다르다. Rich Hickey의 *Simple Made Easy* — 단순함은 한 가지 일을 하는 구조적 속성이고, 쉬움은 익숙함의 주관적 속성이다 |

### 2.4 Law of Leaky Abstractions (누수의 법칙)

| 항목 | 내용 |
|------|------|
| 원어 | "All non-trivial abstractions, to some degree, are leaky." (Joel Spolsky, 2002) |
| 핵심 주장 | 좋은 추상화도 현실의 복잡함을 완전히 숨기지 못한다. 문제를 해결하려면 추상 아래 계층에 대한 이해가 필요하다 |
| 적용 예시 | ORM이 SQL을 숨겨주지만 N+1 쿼리 문제는 ORM만 봐서는 풀 수 없다. TCP가 신뢰성을 약속하지만 패킷 손실·재전송의 비용은 애플리케이션에 새어 나온다 |
| 함의 | 추상화의 가치는 부정하지 않지만, "추상화를 쓰니 아래를 몰라도 된다"는 명제는 거짓이다 |

### 2.5 Single Responsibility Principle (SRP, 단일 책임 원칙)

| 항목 | 내용 |
|------|------|
| 출처 | Robert C. Martin, SOLID 5원칙 중 첫 번째 |
| 핵심 주장 | "A module should have one, and only one, reason to change." — 모듈은 단 하나의 **변경 이유(액터)** 만 가져야 한다 |
| 적용 예시 | `Employee` 클래스에 급여 계산(회계팀)·근태 보고(인사팀)·DB 저장(개발팀) 메서드가 함께 있으면, 한 팀의 요구 변경이 다른 팀 로직을 깨뜨릴 수 있다 |
| 흔한 오해 | "함수는 한 가지 일만 해야 한다"가 아니다. "한 종류의 변경 요구에만 응답해야 한다"가 정확한 정의이다 |

### 2.6 Law of Demeter (LoD, 디미터의 법칙 / Principle of Least Knowledge)

| 항목 | 내용 |
|------|------|
| 출처 | Northeastern University Demeter Project (1987) |
| 핵심 주장 | 객체는 직접 알고 있는 협력자에게만 메시지를 보낸다. "친구의 친구"에게 직접 말 걸지 않는다 |
| 적용 예시 | `order.getCustomer().getAddress().getCity()` 같은 메서드 체인은 LoD 위반의 전형. 중간 단계가 바뀌면 호출부가 모두 깨진다 |
| 실무 활용 | "물어보지 말고 시켜라(Tell, Don't Ask)" — `order.shipTo()` 처럼 행위를 위임한다. 단, DTO나 fluent builder에는 무리하게 적용하지 않는다 |

## 3. 팀과 프로젝트 운영

인력·일정·지표·품질이 엇나가는 문제를 다룬다.

### 3.1 Brooks's Law (브룩스의 법칙)

| 항목 | 내용 |
|------|------|
| 원어 | "Adding manpower to a late software project makes it later." (Fred Brooks, *The Mythical Man-Month*, 1975) |
| 핵심 주장 | 늦어진 프로젝트에 사람을 더 투입하면 오히려 더 늦어진다 |
| 메커니즘 | (1) 신규 인력 학습 곡선(ramp-up) 동안 기존 인력의 시간을 소모, (2) 의사소통 경로가 N(N-1)/2로 증가, (3) 분할 불가능한 작업(임신은 9명이 1개월에 끝낼 수 없다)의 존재 |
| 실무 함의 | 일정 회복 수단으로 인력 추가는 마지막 카드. 우선 범위 축소·병목 식별·기술적 빚 정리를 검토한다 |

### 3.2 Hofstadter's Law (호프스태터의 법칙)

| 항목 | 내용 |
|------|------|
| 원어 | "It always takes longer than you expect, even when you take into account Hofstadter's Law." (Douglas Hofstadter, *Gödel, Escher, Bach*, 1979) |
| 핵심 주장 | 추정에는 항상 낙관 편향이 있다. 그 편향을 고려해도 여전히 모자란다 |
| 적용 예시 | 추정의 자기 참조성 — 버퍼를 추가해도 새 버퍼가 또 부족하다 |
| 실무 활용 | 추정은 분포로 다룬다(P50/P90). 단일 점 추정 대신 범위로 보고하고, 미지 영역에는 명시적 risk margin을 둔다 |

### 3.3 Goodhart's Law (굿하트의 법칙)

| 항목 | 내용 |
|------|------|
| 원어 | "When a measure becomes a target, it ceases to be a good measure." (Charles Goodhart, 1975; Marilyn Strathern, 1997) |
| 핵심 주장 | 지표가 목표가 되는 순간, 사람들은 지표 자체를 최적화하기 시작해 본래 측정하려던 것과 분리된다 |
| 적용 예시 | 코드 커버리지 90%를 목표로 삼은 결과 무의미한 assert로 채워진 테스트가 늘어났지만 핵심 버그는 그대로 |
| 실무 활용 | 단일 지표가 아니라 **지표 묶음(metric basket)** 으로 본다. 지표는 의사결정의 입력이지 의사결정 자체가 아니다 |

### 3.4 Pareto Principle (파레토 법칙 / 80-20 법칙)

| 항목 | 내용 |
|------|------|
| 출처 | Vilfredo Pareto의 부의 분포 관찰을 Joseph M. Juran이 품질관리에 적용 |
| 핵심 주장 | 결과의 80%는 원인의 20%에서 나온다. 정확한 비율보다 분포의 비대칭성이 핵심이다 |
| 적용 예시 | 성능 핫스팟의 80%는 코드 20%에 몰려 있다 — 측정 없이 분산 최적화 금지. 버그 80%는 모듈 20%에서 나온다 — 회귀 테스트 우선순위 |
| 주의 | 80/20은 비유적 비율이다. 데이터로 실제 분포를 확인한 뒤 의사결정의 근거로 쓴다 |

### 3.5 The Boy Scout Rule (보이스카우트 규칙)

| 항목 | 내용 |
|------|------|
| 출처 | Robert C. Martin, *Clean Code* (2008) — 보이스카우트 강령 "Leave the campground cleaner than you found it" 의 차용 |
| 핵심 주장 | 코드는 처음 봤을 때보다 조금이라도 더 깨끗하게 남긴다. 작은 개선의 누적이 품질을 만든다 |
| 적용 예시 | 변경 PR에서 마주친 오타·잘못된 변수명·죽은 코드 한 줄을 함께 정리한다 |
| 주의 | "관련 없는 대규모 리팩토링을 한 PR에 끼워 넣어라"는 뜻이 아니다. 리뷰 가능한 범위 안에서만 적용한다 |

## 4. 요약

| 영역 | 적용 시점 | 핵심 질문 |
|------|----------|-----------|
| 시스템 아키텍처 | 분할·확장·계약 결정 시 | 조직 구조와 시스템 구조가 정렬돼 있는가 (Conway). 단순한 것에서 진화했는가 (Gall). 명세 외 동작에 의존하지 않는가 (Hyrum). 어떤 두 가지를 보장할 것인가 (CAP). 무엇을 엄격히 보내고 무엇을 관대히 받을 것인가 (Postel) |
| 설계와 코드 품질 | 기능·추상화·결합 결정 시 | 지금 필요한가 (YAGNI). 지식 중복인가 코드 중복인가 (DRY). 단순한가 (KISS). 추상화 아래를 알고 있는가 (Leaky). 누가 변경을 요구하는가 (SRP). 친구의 친구에게 말 걸고 있지 않은가 (LoD) |
| 팀과 프로젝트 운영 | 일정·인력·지표 결정 시 | 인력 추가가 답인가 (Brooks). 낙관 편향을 보정한 뒤에도 또 모자라지 않은가 (Hofstadter). 지표가 목표가 됐는가 (Goodhart). 어디 20%에 집중할 것인가 (Pareto). 작은 개선을 누적하고 있는가 (Boy Scout) |

핵심 메시지:

- 작게 시작해서 검증하며 키운다 (Gall, YAGNI, KISS)
- 지식의 단일 출처를 유지하고 결합을 낮춘다 (DRY, SRP, LoD)
- 명세 외 동작과 추상화의 누수를 의식한다 (Hyrum, Leaky, Postel)
- 사람·일정·지표는 직관이 아니라 분포·메커니즘으로 본다 (Brooks, Hofstadter, Goodhart, Pareto)
- 팀 구조가 곧 아키텍처다 (Conway)
