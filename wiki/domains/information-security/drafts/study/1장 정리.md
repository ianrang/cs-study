# 1 시스템 보안

> 목표: 운영체제의 인증·권한·로그·보안설정을 보고 **취약점, 위험, 보완 방법**을 답안으로 쓴다. 이 문서는 KCA 실기 출제기준의 `운영체제별 보안특성 파악`과 `운영체제 보안설정 점검과 보완` 범위를 시험용으로 정리한다.

> 이 장만 학습할 때는 `0 학습 지도 → 1.1~1.5 본문 → 1.6 P1 체크리스트 → 기출 적용` 순서로 본다. 1.7 P3는 시간이 남을 때 확장하고, 마지막에는 1.8의 회독 기준으로 스스로 답을 써 본다.

## 0. 학습 우선순위와 출제 패턴

### 태그 규칙

- **[P1]**: 다음 주 기출 풀이 전 반드시 즉답·서술 가능한 핵심. 최근성·반복성·공식 기준이 모두 강하다.
- **[P2]**: P1을 마친 뒤 연결해서 준비할 변형·실무형 대비 항목.
- **[P3]**: 저빈도 또는 구현 세부. 정의와 보안 목적만 우선 기억한다.
- **[답안]**: 단답형, 서술형, 실무형에서 답을 만드는 방식이다.

### 출제 패턴

1. **용어·파일명 단답형**: `/etc/shadow`, `btmp`, `lastb`, `lastcomm`, 특수권한, PAM 모듈처럼 이름을 정확히 쓴다.
2. **설정·로그 해석형**: 계정·파일 권한·xinetd·로그 한 줄을 보고 무엇이 위험한지, 왜 위험한지, 어떻게 고칠지 쓴다.
3. **Windows/Linux 비교형**: 같은 보안 목적을 각각의 계정·권한·로그·설정 위치로 연결한다.
4. **증거 기반 서술형**: 설정값·로그·명령 결과를 근거로 공격 또는 취약점을 판단하고, 완화 조치를 제시한다.

## 1.1 [P1] Linux 계정·인증·권한

### 1.1.1 [P1] 계정 파일과 필드

- `/etc/passwd`: 계정 기본 정보. 일반적으로 두 번째 필드가 `x`이면 실제 패스워드 해시는 `/etc/shadow`에 있다.
  - 형식: `계정명:x:UID:GID:GECOS:홈디렉터리:로그인셸`
- `/etc/shadow`: 패스워드 해시와 만료 정책을 보호한다.
  - 형식: `계정명:해시:최종변경일:최소일:최대일:경고일:비활성일:만료일:예약필드`
  - 해시 식별자 예: `$1$` MD5, `$5$` SHA-256, `$6$` SHA-512. 식별자는 알고리즘 단서이며, 실제 해시는 salt와 해시값을 함께 포함한다.
  - 패스워드 필드 앞의 `!`는 패스워드 기반 로그인을 잠그는 데 사용된다. 기호의 정확한 조합은 배포판·계정 생성 방식에 따라 달라질 수 있으므로, 시험에서는 **잠금 여부와 보안 목적**을 우선 판단한다.
- `/etc/group`: 그룹명·GID·보조 그룹 구성원을 관리한다.

**[답안]** `shadow`는 패스워드 해시와 만료 정보를 일반 사용자에게 노출하지 않도록 보호한다. 권한이 느슨하면 해시 탈취 후 오프라인 크래킹 위험이 커지므로 root만 읽을 수 있게 제한한다.

### 1.1.2 [P1] PAM과 패스워드 정책

- PAM(Pluggable Authentication Modules)은 인증 정책을 모듈화한다.
  - `auth`: 사용자의 인증 정보 검증
  - `account`: 계정 유효성·접근 가능 시간·잠금 등 계정 상태 확인
  - `password`: 패스워드 변경 정책 처리
  - `session`: 로그인 전후 세션 작업 처리
- 패스워드 정책의 핵심은 길이·문자 종류·사전어·재사용 제한·사용 기간·실패 잠금·세션 타임아웃이다.
- 실패 잠금 기출형에서는 문제에 제시된 `pam_tally.so`의 `deny`, `unlock_time`, `no_magic_root`, `reset`을 그대로 해석한다. 현대 Linux에서 유사한 목적은 `pam_faillock`으로 구현할 수 있지만, 이를 과거 기출의 답으로 바꾸지 않는다.
- `TMOUT`은 PAM 옵션이 아니라 셸의 유휴 세션 타임아웃 환경변수다. 30회처럼 `/etc/profile` 등에 값을 제시하면 `export TMOUT=값` 형태와 유휴 세션 종료 목적을 답한다.
- PAM 모듈·설정 파일·키는 배포판·버전마다 다르므로, **문제에서 제시한 파일·모듈·값을 우선**한다. 품질 정책과 배포판별 세부는 1.7.4의 P3 참고에서 확인한다.

**[답안]** 패스워드 정책은 추측·재사용·무차별 대입으로 인한 계정 탈취를 줄이기 위한 통제다. 길이·복잡도·만료·실패 잠금·유휴 세션 종료를 적용하고, 계정 부여·변경·삭제 이력을 관리한다.

**[P1] Unix 계열별 최소 길이 설정 기출형**

| 운영체제 | 설정 파일 | 최소 8자리 설정 예 |
|---|---|---|
| Linux | `/etc/login.defs` | `PASS_MIN_LEN 8` |
| AIX | `/etc/security/user` | `minlen=8` |
| Solaris | `/etc/default/passwd` | `PASSLENGTH=8` |
| HP-UX | `/etc/default/security` | `MIN_PASSWORD_LENGTH=8` |

위 값은 기출에서 요구한 8자리 설정 예다. 실제 운영에서는 운영체제·버전·PAM 구성과 조직 정책을 확인하며, 문제에서 다른 최소 길이를 주면 해당 값으로 작성한다. Linux의 `/etc/login.defs` 설정만으로 기존 계정이나 PAM 인증 흐름 전체가 항상 강제된다고 단정하지 않고 실제 PAM 정책도 함께 점검한다.

### 1.1.3 [P1] 파일 권한과 특수권한

- 일반 권한: 소유자(user), 그룹(group), 기타(other)에 대해 읽기·쓰기·실행 권한을 설정한다.
- SUID: 실행 파일이 실행 시 **파일 소유자**의 유효 권한으로 동작한다. 불필요한 SUID는 권한 상승 위험이 있다.
- SGID: 실행 파일은 파일 그룹의 유효 권한으로 동작할 수 있고, 디렉터리에서는 새 파일이 디렉터리 그룹을 상속한다.
- Sticky bit: 공용 쓰기 디렉터리에서 파일 소유자·디렉터리 소유자·root 외의 삭제/이름 변경을 제한한다.
- 자주 나오는 점검 명령:

```bash
# SUID가 설정된 일반 파일 찾기
find / -type f -perm -4000

# SGID가 설정된 일반 파일 찾기
find / -type f -perm -2000

# other 쓰기 권한이 있는 일반 파일 찾기
find / -type f -perm -0002

# 소유자 또는 그룹이 없는 파일 찾기
find / \( -nouser -o -nogroup \)
```

- 대표 점검 예: `/etc/passwd`는 일반적으로 `644`, `/etc/shadow`는 일반적으로 `400` 또는 더 제한된 권한을 사용한다. 정확한 기준값은 문제의 운영체제·점검 기준을 따른다.
- 권한 변경·기본 권한 계산도 함께 연결한다.

```bash
# 권한 변경: 소유자 rw, 그룹 r, 기타 r
chmod 644 파일명

# 소유자와 그룹 변경
chown 사용자:그룹 파일명

# 새 파일·디렉터리의 기본 권한 마스크 설정 예
umask 022
```

- `umask`는 허용 권한이 아니라 새 객체의 기본 권한에서 제거할 권한 비트다. 일반적으로 파일은 `666`, 디렉터리는 `777`에서 umask를 적용한다. 예를 들어 `umask 022`이면 일반 파일은 보통 `644`, 디렉터리는 `755`가 된다.

### 1.1.4 [P1] 로그인·감사 로그와 명령

| 기록/명령 | 의미 | 시험 포인트 |
|---|---|---|
| `utmp`, `who`, `w` | 현재 로그인 세션 | 현재 접속자 확인 |
| `wtmp`, `last` | 로그인·로그아웃·재부팅 이력 | 과거 접속 이력 확인 |
| `btmp`, `lastb` | 로그인 실패 이력 | 무차별 대입·비정상 로그인 탐지 |
| `lastlog`, `lastlog` | 계정별 마지막 로그인 정보 | 장기간 미사용·의심 계정 점검 |
| `lastcomm` | process accounting이 켜진 환경의 실행 명령 이력 | 사용자가 실행한 명령 추적 |
| `lsof` | 열린 파일과 이를 사용하는 프로세스 | 의심 포트·삭제된 열린 파일·프로세스 점검 |
| `[P1]` RHEL/CentOS: `/var/log/secure` | 인증·로그인·`sudo` 등 보안 이벤트 | 인증 실패·권한 사용 확인 |
| `[P1]` RHEL/CentOS: `/var/log/messages` | 시스템·서비스·커널/인터페이스 일반 메시지 | 서비스 오류·시스템 이상 확인. CentOS Promiscuous Mode 기출의 기대 경로 |
| `[P2]` Debian/Ubuntu: `/var/log/auth.log` | 인증·로그인·`sudo` 등 보안 이벤트 | 문제에서 Debian/Ubuntu를 명시할 때 사용 |
| `[P2]` Debian/Ubuntu: `/var/log/syslog` | 시스템·서비스 일반 메시지 | 문제에서 Debian/Ubuntu를 명시할 때 사용 |
| `[P2]` `/var/log/audit/audit.log` | `auditd` 감사 이벤트 | 보안 정책·시스템 호출·객체 접근 추적 |

- **현재 P1 암기**: `RHEL/CentOS = secure(인증) / messages(시스템 일반)` 두 개만 정확히 쓴다. 10회 실무형은 CentOS를 명시하고 Promiscuous Mode 관련 로그 경로로 `/var/log/messages`를 요구했다.
- Debian/Ubuntu의 `auth.log`·`syslog`는 현재 P2다. 문제에서 해당 계열을 명시할 때만 적용한다. 실제 로그 경로는 배포판·버전·rsyslog/journald 설정에 따라 달라질 수 있으나, 시험에서는 문제에 제시된 운영체제와 로그 형식을 우선한다.

**[답안]** `btmp`/`lastb`는 로그인 실패 흔적을 확인하는 데 사용한다. 다수의 실패가 반복되면 무차별 대입 또는 계정 오남용 가능성을 판단하고, 계정 잠금·접근원 제한·로그 보존·원인 조사를 수행한다.

### 1.1.5 [P2] Shell·inode 시간·프로세스·메모리 취약점

- Shell은 사용자의 명령을 해석해 커널·프로그램 실행으로 연결하는 명령 인터페이스다.
- 핵심 기능은 `명령 해석·실행`, 환경변수·작업 환경 제공, 입출력 재지정(redirection), 명령 간 파이프 연결, 조건·반복·변수 등을 이용한 shell script 실행이다.
- Shell 자체가 커널은 아니다. 사용자의 명령을 해석하고 필요한 system call과 프로그램 실행을 연결하며, 권한 검사는 커널과 대상 자원의 접근통제 정책이 수행한다.

**[답안]** Shell은 사용자와 운영체제 사이에서 명령을 해석·실행하는 인터페이스이며, 환경 설정, 입출력 재지정, 파이프 및 스크립트 기능을 제공한다.

- `atime`: 마지막 접근 시간, `mtime`: 파일 내용 변경 시간, `ctime`: inode 메타데이터 변경 시간이다. `ctime`은 생성 시간이 아니다.
- 프로세스는 일반적으로 `fork()`로 생성한 뒤 `exec()` 계열 호출로 새 프로그램 이미지를 적재한다.
  - `SIGINT(2)`: 인터럽트, `SIGKILL(9)`: 강제 종료, `SIGSTOP(19)`: 정지
- `/proc`는 실행 중인 프로세스와 커널 상태를 파일 형태로 노출하는 가상 파일시스템이다. PID 디렉터리, 명령행, 열린 파일, 메모리·네트워크 상태를 확인하는 단서로 사용한다.
- 버퍼 오버플로우는 버퍼 경계를 넘는 입력이 인접 메모리를 덮어써 프로그램 흐름·데이터를 훼손할 수 있는 취약점이다.
  - 원인: 길이 검증 없는 복사·입력 처리
  - 대응: 입력 길이·형식 검증, 안전한 API와 오류 처리, 컴파일러 보호(stack canary), ASLR, NX/DEP, 패치
  - `strncpy()`만 사용한다고 자동으로 안전해지는 것은 아니다. 종료 문자·버퍼 길이를 함께 확인해야 한다.

## 1.2 [P1] Linux 서버 보안설정 점검과 보완

### 1.2.1 [P1] 서비스 최소화와 xinetd 설정

- 원칙: 사용하지 않는 서비스·계정·포트는 제거 또는 비활성화하고, 필요한 서비스만 허용 대상·시간·동시 연결 수를 제한한다.
- xinetd는 요청이 들어올 때 서비스를 실행·관리하는 슈퍼 데몬이다. 최신 배포판은 systemd를 주로 사용하지만, 시험에서는 xinetd 설정 해석이 반복된다.

| 지시어 | 의미 | 보안 판단 |
|---|---|---|
| `disable = yes/no` | 서비스 비활성화/활성화 | 불필요 서비스는 `yes`로 비활성화 |
| `only_from = IP` | 허용 원본 IP·대역 | 관리망 등 필요한 대상만 허용 |
| `no_access = IP` | 차단 원본 IP·대역 | 알려진 비인가 대역 차단 |
| `access_times = 09:00-18:00` | 서비스 허용 시간 | 불필요한 야간 노출 축소 |
| `instances = 10` | 최대 동시 인스턴스 | 자원 고갈 완화 |
| `per_source = 3` | 원본별 최대 연결 수 | 단일 출발지의 과도한 연결 완화 |
| `cps = 50 10` | 초당 연결 한도·초과 시 대기 | 과도한 연결 시도 완화 |

- TCP Wrapper의 `hosts.allow`, `hosts.deny`는 libwrap을 사용하는 레거시 서비스의 IP 기반 접근통제 수단이다. 시험에서는 **허용 우선·차단 정책과 IP 제한 목적**을 이해한다.

### 1.2.2 [P1] 계정·권한·파일 점검

| 점검 대상 | 취약 상태 | 보완 방향 |
|---|---|---|
| 계정 | 불필요 계정, 공유 계정, 미사용 관리자 계정 | 제거·잠금·개인별 계정 발급·권한 정기 검토 |
| 패스워드 | 짧음, 재사용, 실패 잠금 미설정 | PAM 품질·만료·실패 잠금 정책 적용 |
| 파일·디렉터리 | world-writable, 과도한 SUID/SGID, 소유자 없음 | 최소권한·소유자 정정·불필요 특수권한 제거 |
| 중요 파일 | 패스워드·설정 파일의 과도한 읽기/쓰기 권한 | 관리자만 변경·필요 최소 사용자만 읽기 |
| 무결성 | 기준 파일과 현재 파일이 다름 | 변경 승인 여부 확인, Tripwire 등으로 기준선 비교 |

- 점검 명령은 1.1.3의 `find`, `chmod`, `chown`, `umask`를 사용한다. 점검 결과를 발견하는 데서 끝내지 말고 `업무상 필요 여부 확인 → 소유자·권한 정정 → 변경 기록 → 재점검` 순서로 처리한다.
- `find -perm -MODE`은 MODE의 모든 비트가 설정된 대상을, `find -perm /MODE`은 MODE 중 하나 이상이 설정된 대상을 찾는다.

### 1.2.3 [P1/P2] 로그·원격접속·버전·패치 점검

#### [P1] 기출형 판단과 답안

- 운영체제·커널·서비스 버전이 문제의 배너·로그·화면에 제시되면 지원 종료, 알려진 취약점, 상세 정보 노출 여부를 판단한다. 명령으로 버전을 직접 조회하는 방법은 1.7.5의 P3 참고다.

| 점검 축 | 확인할 증거 | 대표 보완 |
|---|---|---|
| 로그 | 로그인 성공/실패, 권한 변경, 서비스 오류, 비정상 프로세스 | 로그 생성·보관·권한 제한·정기 분석 |
| Telnet·FTP | 인증정보·데이터의 평문 전송, root 직접 로그인, 상세 버전 배너 | Telnet은 SSH로, FTP는 SFTP/FTPS로 전환하고 root 직접 로그인·상세 배너를 제한 |
| 버전 노출·패치 | 배너·오류 페이지·서비스 응답의 OS/커널/미들웨어 버전, 지원 종료·취약 버전 | 불필요한 상세 배너·오류 제거, 자산·버전 식별 → 영향 평가 → 테스트 → 패치·배포 → 결과 기록 |
| 백업·복구 | 복구 불가·검증되지 않은 백업 | 중요 설정·로그·데이터의 백업과 복구 시험 |

**Linux root 로그인 터미널 제한 — P1 정확 경로**

- **TTY**는 로그인에 사용되는 터미널 장치의 식별자다. 물리 콘솔·가상 콘솔·직렬 콘솔 등 “어느 터미널에서 로그인하는가”를 뜻하며, 사용자 계정명이나 허용 IP 목록이 아니다.
- `/etc/securetty`에는 **root 로그인을 허용할 TTY 장치명**을 한 줄씩 적는다. `login` 또는 `pam_securetty`가 적용된 서비스는 root가 접속한 TTY가 이 목록에 있을 때만 인증을 계속한다. 일반 사용자 계정에는 적용하지 않는다.
- 따라서 이 파일은 “필요한 계정만 허용”하는 계정 목록이나 일반적인 원격접속 허용 목록이 아니다. **root가 직접 로그인할 수 있는 터미널을 제한하는 설정**이다. 6회와 30회 기출에서 Linux root 로그인 제한 파일로 직접 출제됐다.
- 표준 OpenSSH의 root 로그인 허용 여부는 별도다. `/etc/securetty`만으로 SSH root 로그인을 막는다고 쓰면 안 되며, SSH는 다음 P2의 `PermitRootLogin`으로 제어한다.

**[답안]** `/etc/securetty`는 root가 직접 로그인할 수 있는 TTY 장치 목록을 관리하는 파일이다. 허용된 터미널만 남겨 root 직접 로그인 경로를 제한한다. 계정·IP 목록을 관리하는 파일이나 SSH root 로그인 설정 파일은 아니다.

**[답안]** Telnet과 FTP는 인증정보·데이터가 평문으로 노출될 수 있다. Telnet은 SSH로, FTP는 SFTP 또는 FTPS로 전환하고 root 직접 로그인과 상세 버전 배너를 제한한다.

#### [P2] SSH의 정확 설정 위치

- SSH의 root 로그인 허용 여부는 `/etc/ssh/sshd_config`의 `PermitRootLogin` 지시어로 점검한다. root SSH 로그인을 차단하는 대표 값은 `PermitRootLogin no`다.
- 현재 1~31회 데이터에서는 이 경로·지시어를 직접 빈칸으로 요구한 문항은 확인되지 않았다. 따라서 `경로 → 지시어 → no의 의미`까지만 P2로 준비하고, 관리 IP 제한·인증 방식·OpenSSH 버전별 세부는 P3로 둔다.

**[답안 템플릿]** `[설정/로그]는 [위험]을 발생시킬 수 있다. [근거] 때문에 비인가 접근·권한 상승·정보 노출 가능성이 있다. 따라서 [서비스/계정/권한]을 최소화하고 [구체적 설정·패치·로그 점검]을 적용한다.`

## 1.3 [P1/P2] 계정관리·Windows 인증·접근통제·감사

### 1.3.1 [P2] Windows 보안 구성요소

| 구성요소 | 역할 | 시험 포인트 |
|---|---|---|
| LSA/LSASS | 로컬 보안 정책과 인증 절차를 관리 | 인증·보안 정책의 중심 |
| SAM | 로컬 계정과 패스워드 해시 정보를 관리 | 로컬 계정 정보 보호 |
| SRM | 커널 수준의 접근 토큰·ACL 검사와 감사 이벤트 생성에 관여 | 객체 접근통제·감사 |
| SID | 보안 주체를 식별하는 고유 식별자 | 계정 생성 시 부여되고, 로그인 시 새로 발급되는 값이 아님 |

- LM 해시는 오래된 DES 기반 방식으로 취약하다. NTLM 계열은 챌린지/응답 방식이며, 도메인 환경에서는 Kerberos가 주된 인증 방식이다.
- 계정 보안의 핵심은 기본 Administrator 계정 보호, Guest 비활성화, 최소권한 그룹 부여, 계정 공유 금지, 로그인·권한 변경 감사다.
- **SID(Security Identifier)**는 계정·그룹을 식별하는 전체 식별자다. 예: 기본 Administrator 계정의 SID는 `S-1-5-21-<컴퓨터/도메인 식별자>-500`처럼 표현할 수 있다.
- **RID(Relative Identifier)**는 SID의 **마지막 숫자**로, 같은 컴퓨터 또는 도메인 안에서 계정·그룹을 구분한다. 따라서 `500`·`501`만으로는 SID 전체가 아니며 전역적으로 고유하지도 않다.

| 기본 계정 | 전체 SID의 끝부분 | RID |
|---|---|---:|
| Administrator | `...-500` | `500` |
| Guest | `...-501` | `501` |

- 일반 계정의 RID는 환경마다 달라지므로 특정 숫자 범위를 보안 판단 근거로 단정하지 않는다. 계정 이름을 바꿔도 SID의 끝 RID는 바뀌지 않을 수 있으므로, 이름만 보고 기본 Administrator·Guest 여부를 판단하지 않는다.
- **주의**: `Administrators`는 계정이 아니라 기본 제공 **그룹**이며, 대표 SID는 `S-1-5-32-544`다. `Administrator` 계정의 RID `500`과 혼동하지 않는다.
- UAC(User Account Control)는 관리자 권한이 필요한 작업에서 권한 상승을 확인·통제한다. UAC 팝업이 나타났다는 사실만으로 악성행위를 단정하지 않고, 실행 파일·게시자·요청한 작업·사용자 의도를 함께 확인한다.

### 1.3.2 [P1] NTFS 권한·암호화·이벤트 로그

- NTFS ACL은 사용자·그룹별 권한을 제어한다. 공유 권한과 NTFS 권한이 함께 적용될 수 있으므로, 최소권한 원칙으로 불필요한 쓰기·변경 권한을 제거한다.
- EFS는 NTFS 파일·폴더 단위 암호화 기능이고, BitLocker는 볼륨 단위 암호화 기능이다. 둘은 적용 단위와 운영 목적이 다르다.
- 이벤트 뷰어(`eventvwr.msc`)에서 `Security`, `System`, `Application` 로그를 중심으로 로그인 성공·실패, 계정 관리, 개체 접근, 정책 변경, 시스템·응용 프로그램 오류를 확인한다.
- Windows 서비스 로그의 대표 경로는 IIS site log `%SystemDrive%\inetpub\logs\LogFiles\W3SVC*`, HTTP API 오류 `%SystemRoot%\System32\LogFiles\HTTPERR`, DHCP Server `%SystemRoot%\System32\DHCP`다. 기출에서 `W3SVC1`·`MSFTPSVC1` 같은 식별자만 요구할 수 있고 base path는 설치·역할·버전·설정에 따라 달라질 수 있으므로 문제에서 제시한 환경을 우선한다.
- 로그는 필요한 보관 기간과 용량을 정하고, 덮어쓰기·삭제·변조 위험을 줄이며 중앙 수집 또는 별도 보관을 고려한다.
- 로그 용량 계산형은 문제에서 준 단위로 계산한다.

```text
필요 로그 용량 = 이벤트 1건의 크기 × 일일 발생 건수 × 보관 일수
```

단위가 byte로 주어졌다면 마지막에 KB/MB 변환 요구가 있는지 확인하고, 이벤트 뷰어의 해당 로그 속성에서 최대 로그 크기와 덮어쓰기 정책을 함께 설정한다.

### 1.3.3 [P2] EAM과 IAM

- **EAM(Enterprise Access Management)**은 서버·운영체제·DB 등 내부 시스템 계정과 애플리케이션 접근계정을 중앙에서 관리하는 접근관리 체계다.
- EAM은 내부 시스템·애플리케이션 중심이어서 직원·고객·협력업체 등 조직 전체 신원을 포괄하기 어렵고, 계정 생성·권한 변경·회수를 수작업에 의존하면 운영 부담·비용과 권한 회수 지연이 커질 수 있다.
- **IAM(Identity and Access Management)**은 내부·외부 사용자의 신원과 계정·권한을 전사적으로 관리한다. 입사·이동·휴직·퇴사와 협력사 계약 상태 같은 인사·업무 이벤트에 맞춰 계정 생성, 권한 부여·변경, 정기 검토, 회수·삭제를 자동화한다.
- IAM은 SSO·MFA·RBAC 같은 인증·접근통제 수단과 연계하되 그 자체와 동일한 개념은 아니다. 4.6의 접근통제 모델은 권한을 결정하는 원리이고, IAM은 그 정책과 계정 생명주기를 운영하는 체계다.
- EAM 약어를 `Extranet Access Management`로 사용하는 자료·제품도 있으므로 약어만 보고 범위를 단정하지 않는다. 30회 기출처럼 문제가 영문 풀이나 관리 대상을 제시하면 그 문맥을 우선하며, 이 절의 답안은 해당 기출의 `Enterprise Access Management` 기준이다.

**[답안]** EAM과 IAM의 공통 목적은 계정과 접근권한을 중앙에서 통합 관리하는 것이다. EAM은 내부 서버·OS·DB·애플리케이션 계정 중심이어서 조직 전체 사용자로 확장하기 어렵고 수작업 운영 부담이 생길 수 있다. IAM은 직원·고객·외부 사용자·협력업체까지 관리 범위를 넓히고 계정 생성·권한 부여·변경·회수의 생명주기를 자동화한다.

## 1.4 [P1] Windows 서버 보안설정 점검과 보완

### 1.4.1 [P1] NetBIOS·공유·원격 세션

- NetBIOS over TCP/IP가 필요하지 않은 환경에서는 비활성화를 검토한다. 비활성화 전에는 레거시 WINS/NetBT 의존 서비스가 없는지 확인해야 한다.
- 대표 경로: `ncpa.cpl` → 네트워크 어댑터 속성 → `Internet Protocol Version 4 (TCP/IPv4)` → 고급 → WINS → `NetBIOS over TCP/IP 사용 안 함`.
- 공유·세션 점검 명령:

```bat
net share
net session
net session \\대상컴퓨터 /delete
```

## 1.5 [P2] 무결성·악성코드·취약점 대응

- 파일 무결성 점검은 기준선의 파일 해시·속성·권한과 현재 상태를 비교해 비인가 변경을 탐지한다. Tripwire는 대표적인 무결성 점검 도구다.

**[P2] PE(Portable Executable) 악성코드 분석 방식**

| 방식 | 수행 방법 | 장점·한계 |
|---|---|---|
| 자동 분석 | 백신·정적 분석기·sandbox 등에 파일을 입력해 특징·행위를 자동 수집 | 빠르고 반복 가능하지만 우회·오탐·환경 인식에 취약 |
| 반자동 분석 | 분석가가 자동 도구 결과를 바탕으로 문자열·import·section·행위와 의심 지점을 추가 확인 | 속도와 정밀도의 절충이지만 분석가 판단이 필요 |
| 수동 분석 | disassembler·debugger로 코드 흐름, API 호출, unpacking·복호화 과정을 직접 추적 | 복잡한 악성코드에 유용하지만 시간과 전문성이 많이 필요 |

분석은 원본 hash와 획득 경로를 기록하고 격리된 환경에서 복제본으로 수행한다. 정적 분석은 파일을 실행하지 않고 header·section·import·문자열 등을 확인하고, 동적 분석은 통제된 sandbox에서 process·file·registry·network 행위를 관찰한다. 자동·반자동·수동은 도구 사용량과 분석가 개입 정도의 구분이고, 정적·동적은 실행 여부와 관찰 방식의 구분이므로 같은 축으로 혼동하지 않는다.

### 1.7.3 Linux 프로세스와 PCB

- PCB(Process Control Block)는 운영체제가 **현재 실행 중인 프로세스를 생성·실행·중단·재개·스케줄링하기 위해 유지하는 제어 정보**다. 운영체제마다 실제 구조와 필드 구성은 다르므로 모든 필드를 외우지 않는다.
- PCB와 프로세스 관리 정보에는 대표적으로 PID·상태, 프로그램 카운터·레지스터 같은 실행 문맥, 스케줄링 정보, 메모리·열린 파일·자격증명(UID/GID 등) 관련 정보가 연결된다.
- `fork()`는 부모 프로세스를 바탕으로 **자식 프로세스를 새로 생성**한다. 자식은 새 PID를 받고 부모 PID(PPID)를 통해 부모와 연결된다.
- `exec()` 계열은 **현재 프로세스를 새로 만들지 않고**, 그 프로세스가 실행할 프로그램 이미지를 다른 프로그램으로 교체한다. 일반적인 명령 실행 흐름은 `쉘 → fork()로 자식 생성 → 자식이 exec()로 대상 프로그램 실행`이며, `exec()` 뒤에도 PID는 유지된다.

| 구분 | 시험에서 연결할 개념 | 핵심 구분 |
|---|---|---|
| 프로세스 식별 | PID·PPID, 프로세스명·명령행·실행 경로 | 현재 어떤 프로세스인지와 부모-자식 관계를 확인 |
| 권한·현재 상태 | UID/GID, 상태, 열린 파일·메모리 등 | 현재 어떤 권한과 자원을 사용 중인지 확인 |
| 실행 이력 | 감사 로그, process accounting의 `lastcomm`, 셸 이력 등 | **PCB에 저장되는 정보가 아니다.** 누가 언제 어떤 명령을 실행했는지는 별도의 기록으로 확인 |
| 비정상 프로세스 점검 | 예상 밖의 이름·실행 경로·부모 프로세스, 과도한 권한, 설명되지 않는 포트·열린 파일 | 한 징후만으로 악성이라고 단정하지 않고 기준선·로그·네트워크 증거를 함께 대조 |

- 따라서 문제에서 PCB를 물으면 “프로세스를 관리하는 제어 정보”와 `fork()`·`exec()`의 차이를 답한다. 프로세스 점검 문제에서는 PID/PPID·권한·현재 상태를 확인하고, **실행 이력은 PCB가 아니라 로그·회계 기록으로 확인한다**고 구분한다.

### 1.7.4 [P3] PAM·패스워드 정책의 배포판·세대별 세부

이 절은 모듈·파일·키가 문제에 직접 제시되었을 때 **정책의 종류와 효과를 구분하기 위한 참고**다. 아래 이름·경로·기본값 전체를 통암기하지 않는다. P1 직접 기출은 1.1.2의 PAM 4유형, `pam_tally.so` 잠금 옵션, `TMOUT`, 그리고 최소 길이 설정 표다.

| 정책 영역 | 대표 모듈·파일·키 | 시험에서 이해할 내용 |
|---|---|---|
| 패스워드 품질 | `pam_pwquality`, `/etc/security/pwquality.conf`, `minlen`, `minclass`, `retry`, `difok` | 길이·문자 종류·재입력 횟수·기존 비밀번호와의 차이를 검사한다. `pam_pwquality`는 `password` 스택에 연결되는 품질 점검 모듈이다. |
| 레거시 품질 모듈 | `pam_cracklib` | RHEL 6 등 오래된 환경의 품질 점검 모듈이다. RHEL 7에서는 `pam_pwquality`가 이를 대체했다. 문제에 나온 모듈명을 다른 이름으로 바꾸지 않는다. |
| 인증 실패 잠금 | 과거 기출: `pam_tally.so`의 `deny`, `unlock_time`, `no_magic_root`, `reset`; 현대 예: `pam_faillock` | `deny`는 실패 횟수 임계값, `unlock_time`은 자동 잠금 해제 시간이다. 모듈 이름과 PAM 스택 구성은 세대별로 다르므로 문제의 표기를 그대로 답한다. |
| RHEL 계열 PAM 공통 구성 | `/etc/pam.d/system-auth`, `/etc/pam.d/password-auth` | RHEL 계열에서 여러 서비스가 공통으로 참조할 수 있는 구성이다. RHEL 8 이상에서는 `authselect`가 파일을 관리할 수 있으므로 실제 운영에서 파일을 임의로 수정한다고 단정하지 않는다. |
| Debian 계열 PAM 공통 구성 | `/etc/pam.d/common-auth`, `/etc/pam.d/common-password` 등 | `common-auth`는 인증 흐름, **패스워드 품질·변경 정책은 `common-password`**와 연결해 본다. 배포판별 파일명을 보편 정답으로 외우지 않는다. |
| 셸 유휴 세션 종료 | `/etc/profile` 등의 `TMOUT` | PAM 정책이 아니다. 셸이 일정 시간 입력이 없으면 세션을 종료하도록 하는 환경변수다. |
| 패스워드 기간 기본값 | `/etc/login.defs`의 `PASS_MAX_DAYS`, `PASS_MIN_DAYS`, `PASS_WARN_AGE` | 각각 최대 사용일, 변경 최소 간격, 만료 전 경고일을 뜻한다. 새 계정 생성 시 기본값에 해당하며 기존 계정에 자동으로 소급 적용된다고 단정하지 않는다. |

- `/etc/login.defs`의 `PASS_MIN_LEN`은 24회 Linux 최소 길이 기출에서 요구한 **시험용 레거시 설정값**이다. 최신 운영체제에서 같은 키의 지원 여부와 실제 강제 범위는 PAM·배포판·버전에 따라 다르므로, 기출 답안과 현재 운영 설정을 혼동하지 않는다.
- 숫자 자체를 보편 정답으로 외우지 않는다. 문제에 주어진 값으로 `최소 길이 강화`, `문자 종류·사전어·유사 비밀번호 제한`, `연속 실패 잠금`, `유휴 세션 종료`, `변경 주기·경고 관리` 중 어떤 정책인지 연결한다.
- 답안 원칙: **문제의 운영체제 → 제시 파일·모듈 → 제시 키·값 → 해당 통제 목적** 순서로 판단한다. 같은 목적의 현대 모듈이나 다른 배포판 경로를 임의로 치환하지 않는다.

### 1.7.5 레거시 서비스·운영 확인 명령 세부

- TCP Wrapper: libwrap을 사용하는 서비스에서 `hosts.allow`, `hosts.deny`로 접근을 제한하는 레거시 방식이다.
- `net share`는 공유 목록 확인, `net session`은 서버 세션 확인에 사용한다. 실제 운영 명령은 대상·권한·영향을 확인한 뒤 수행한다.
- 운영체제·커널 정보를 확인하는 대표 명령은 다음과 같다. 현재 1~31회 기출에서는 명령 자체를 쓰게 한 문항을 확인하지 못했으므로, P1 답안처럼 통암기하지 않는다.

```bash
# Linux 운영체제·커널 정보
cat /etc/os-release
uname -a

# Windows 운영체제 정보
systeminfo
```

- `EFS`와 `BitLocker`의 차이, LM/NTLM/Kerberos의 세부 프로토콜 비교, 레지스트리 자동 실행 위치는 시간이 남을 때 P3 기출과 함께 확장한다.

### 1.7.6 P3 학습 완료 기준

1. 레지스트리 하이브 5개를 역할과 함께 구분한다.
2. Administrator·Guest·SYSTEM·Administrators·Users·Backup Operators의 권한 위험을 한 줄로 설명한다.
3. PCB의 목적, `fork()`/`exec()` 차이, 현재 프로세스 관리 정보와 실행 이력 로그의 차이를 설명한다.
4. `pam_pwquality` 품질 정책, `pam_tally`/`pam_faillock` 실패 잠금, 셸 `TMOUT`, `PASS_*` 기간 기본값이 서로 다른 정책 영역임을 구분하고, 문제의 모듈·경로를 임의로 치환하지 않는다.

## 1.8 이 장만 보는 최종 회독 순서

### 1회독: 논리 흐름 이해

`계정 식별 → 인증 정책 → 권한 부여 → 로그 기록 → 취약 설정 점검 → 보완·재점검` 흐름으로 읽는다. 명령어를 따로 외우기보다 각 명령이 이 흐름의 어느 증거를 확인하거나 통제하는지 연결한다.

### 2회독: P1 필수와 P2 확장 회상

아래 질문을 문서를 가리고 답한다.

**P1 필수**

1. `/etc/passwd`, `/etc/shadow`, `/etc/group`의 역할과 주요 필드는 무엇인가?
2. PAM의 네 유형과 패스워드 품질·실패 잠금·세션 종료 정책은 어떻게 연결되는가?
3. Solaris·Linux·AIX·HP-UX의 최소 길이 설정 파일과 키는 무엇인가?
4. SUID·SGID·sticky bit의 의미와 위험한 파일을 찾는 명령은 무엇인가?
5. `utmp/wtmp/btmp/lastlog`와 `last/lastb/lastcomm/lsof`는 무엇을 확인하며, RHEL/CentOS의 `secure/messages`는 각각 무엇을 기록하는가?
6. `only_from`, `no_access`, `instances`, `access_times`가 제한하는 것은 무엇인가?
7. 불필요 계정·평문 원격서비스·버전 노출·패치 누락을 어떻게 점검하고 보완하는가?
8. NTFS ACL의 보안 목적과 EFS·BitLocker의 적용 단위 차이는 무엇인가?
9. NetBIOS·Windows 공유·원격 세션을 어떻게 점검하며 DHCP 로그 경로는 무엇인가?
10. 이벤트 로그 필요 용량을 계산하고 최대 크기·덮어쓰기 정책에 어떻게 반영하는가?

**P2 확장**

11. LSA/LSASS·SAM·SRM·SID/RID의 역할은 어떻게 다른가?
12. Shell의 역할과 명령 실행·환경·리다이렉션·파이프·스크립트 기능은 무엇인가?
13. EAM의 범위·한계와 IAM의 계정 생명주기 자동화는 어떻게 다른가?
14. Tripwire와 취약점 진단 도구의 목적, PE의 자동·반자동·수동 분석은 어떻게 다른가?

### 3회독: 답안 작성 연습

- 단답형: 용어·경로·명령을 정확히 쓴다.
- 서술형: `정의/상태 → 위험/판단근거 → 설정·조치` 세 단으로 쓴다.
- 실무형: 먼저 소문항 수를 세고, 각 번호에 `증거·판단·조치`를 빠짐없이 대응한다.

### 학습 완료 판정

- P1 즉답 목록과 P1 필수 10문항을 90% 이상 설명할 수 있다.
- P2 확장 4문항은 P1 기준을 충족한 뒤 각각의 채점 키워드를 자료 없이 쓴다.
- Linux 설정형 1문제와 Windows 로그·설정형 1문제를 각각 15분 안에 서술할 수 있다.
- 틀린 항목은 해당 본문으로 돌아가 보완하고, P3는 P1 기준을 충족한 뒤 학습한다.
